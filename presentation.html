SQL : le langage qui sert à créer les tables, puis à lire et modifier les données. Trigger : du code que la base déclenche toute seule quand une table change.

On a choisi deux profils dès le départ : Léa, la bibliothécaire, qui prête et reprend les tomes au comptoir, et Marc, le gérant, qui suit la popularité des séries sans rien modifier. » — REPÈRES : Les flèches suivent les clés étrangères : tomes pointe vers series, emprunts pointe vers tomes et vers lecteurs. La seule table volumineuse est emprunts : 200 000 emprunts rendus générés avec generate_series sur 600 jours, plus 5 emprunts en cours tapés à la main pour la démo. Inès (lecteur 1) en a déjà 3 : elle est au maximum. Deux profils choisis dès le départ : quelqu’un qui fait le travail courant, quelqu’un qui contrôle sans modifier. — LES TERMES : Table : un ensemble de lignes qui ont toutes les mêmes colonnes. Clé primaire (id serial) : l’identifiant unique de chaque ligne ; serial le numérote automatiquement. Clé étrangère (REFERENCES) : une colonne qui pointe vers la clé primaire d’une autre table ; la base refuse une valeur qui n’existe pas en face. NULL : l’absence de valeur ; un rendu_le à NULL veut dire que le tome n’est pas encore rendu. generate_series : une fonction qui produit une suite de nombres (1, 2, 3…) ; on en tire 200 000 lignes en calculant chaque colonne à partir du numéro. Utilisateur (lea, marc) : un compte qui peut se connecter à la base.

La démo qui suit prend les quatre notions dans l’ordre de la trame imposée. — LES TERMES : Fonction : du code stocké dans la base, appelé dans une requête, qui renvoie une valeur. Procédure : du code stocké, lancé avec CALL, qui agit sur les données sans renvoyer de valeur. PL/pgSQL : le langage de PostgreSQL pour écrire fonctions, procédures et triggers, avec des IF et des messages d’erreur. Trigger : du code déclenché automatiquement par un événement sur une table, ici avant chaque INSERT. Vue : une requête enregistrée sous un nom, qu’on interroge comme une table ; elle ne stocke rien. Rôle : un groupe de droits dans PostgreSQL ; NOLOGIN veut dire qu’on ne peut pas s’y connecter, il sert seulement à porter les droits. Index : une structure qui retrouve des lignes sans lire toute la table, comme l’index à la fin d’un livre. EXPLAIN ANALYZE : exécute la requête et affiche la stratégie choisie et le temps réel.

À DIRE : « Premier point, les rôles. Je deviens Léa avec SET ROLE lea. Elle peut lire sa vue, emprunts_comptoir : on voit les 5 emprunts en cours. Par contre, si elle essaie de lire l’e-mail d’un lecteur dans la table lecteurs, la base refuse : permission denied. Je reviens avec RESET ROLE et je deviens Marc. Il lit sa vue de statistiques, mais s’il essaie d’ajouter un emprunt, c’est refusé. Les droits sont donnés aux rôles-métiers, bibliothecaire et gerant, et pas aux personnes : si Léa quitte la bibliothèque, on supprime son compte sans toucher aux droits du métier. » — REPÈRES : Requêtes dans la partie 1 de demo.sql. SET ROLE lea, puis RESET ROLE ; SET ROLE marc, puis RESET ROLE. À dire : les droits sont donnés aux rôles-métiers bibliothecaire et gerant, pas aux personnes. lea et marc héritent de leur rôle. Le bibliothécaire peut insérer un emprunt et mettre à jour la seule colonne rendu_le ; il n’a aucun droit sur lecteurs, series ni tomes. Le gérant ne lit que sa vue. On peut aussi montrer que marc ne lit pas emprunts_comptoir : permission denied for view emprunts_comptoir. — LES TERMES : SET ROLE : prendre l’identité d’un rôle pour la suite de la session ; RESET ROLE revient au compte de départ. GRANT : donner un droit (SELECT pour lire, INSERT pour ajouter, UPDATE pour modifier) sur une table ou une vue à un rôle. Droit par colonne : GRANT UPDATE (rendu_le) ne permet de modifier que cette colonne. permission denied : l’erreur renvoyée quand le rôle n’a pas le droit demandé. Héritage (IN ROLE) : lea reçoit tous les droits du rôle bibliothecaire. Moindre privilège : chaque compte n’a que les droits dont il a besoin. DCL : la partie de SQL qui gère les droits (GRANT, REVOKE).

À DIRE : « Deuxième point, la vue. Sans rôle, la table lecteurs contient tout : nom complet, e-mail, téléphone, ville. En tant que Léa, la vue emprunts_comptoir ne montre que le prénom et l’initiale, Inès L., avec la série, le tome, le nombre de jours et si l’emprunt est en retard. La vue fait deux choses : elle cache la complexité, trois jointures et un filtre, et elle protège les données personnelles. La vue du gérant, stats_series, ne montre que des chiffres par série, aucun lecteur. » — REPÈRES : Partie 2 de demo.sql. D’abord, sans rôle : SELECT * FROM lecteurs WHERE id = 1 montre tout (nom, e-mail, téléphone, ville). Puis SET ROLE lea et SELECT lecteur, serie, tome, jours, en_retard FROM emprunts_comptoir WHERE lecteur_id = 1 : Léa ne voit que « Inès L. ». La vue cache la complexité (trois jointures et le filtre sur rendu_le) et protège les données personnelles. Le rôle a le droit sur sa vue, pas sur les tables. — LES TERMES : Jointure (JOIN) : assembler les lignes de deux tables qui vont ensemble, par exemple un emprunt et son lecteur. CTE (WITH … AS) : une sous-requête nommée, écrite avant la requête principale pour la rendre lisible. Agrégat (count, avg) avec GROUP BY : un calcul qui résume plusieurs lignes en une seule, ici une ligne par série. Fonction de fenêtre (sum(…) OVER ()) : un calcul sur plusieurs lignes qui ne les regroupe pas ; ici le total de tous les emprunts, pour calculer le pourcentage de chaque série. Abstraction : la vue cache la complexité des jointures et les colonnes sensibles.

À DIRE : « Troisième point, les index. Je supprime l’index sur lecteur_id et je lance EXPLAIN ANALYZE sur l’historique d’un lecteur : PostgreSQL fait un Seq Scan, il lit les 200 000 lignes. Je recrée l’index, je relance : il passe en Bitmap Index Scan, et le temps tombe de quelques millisecondes à quelques centièmes. On a choisi lecteur_id parce que PostgreSQL n’indexe pas les clés étrangères tout seul, et que notre trigger compte les emprunts d’un lecteur à chaque insertion. Même chose pour la date d’emprunt : une journée, c’est 333 lignes sur 200 000. Les temps varient selon la machine, ce qui compte c’est le changement de plan. » — REPÈRES : Partie 3 de demo.sql : DROP INDEX, EXPLAIN ANALYZE (Seq Scan), CREATE INDEX, EXPLAIN ANALYZE (Bitmap Index Scan). Lancer chaque EXPLAIN ANALYZE deux fois et lire la seconde mesure. Les chiffres de la diapo sont ceux du README ; ceux du direct seront un peu différents, ce qui compte c’est le changement de plan et l’écart. Avant l’index, PostgreSQL lit 199 905 lignes pour rien. — LES TERMES : Plan d’exécution : la stratégie que PostgreSQL choisit pour exécuter une requête. Seq Scan (Sequential Scan) : lire toute la table, ligne par ligne ; Parallel Seq Scan : la même lecture répartie sur plusieurs processus. Index Scan : PostgreSQL cherche dans l’index puis va lire seulement les lignes trouvées. Bitmap Index Scan : il note d’abord dans l’index l’emplacement de toutes les lignes trouvées, puis les lit dans l’ordre du disque, plus rapide quand il y en a plusieurs. B-tree : le type d’index par défaut, un arbre trié qui trouve une valeur en quelques étapes. ms : milliseconde, un millième de seconde.

À DIRE : « Dernier point, le trigger, et je le montre en tant que Léa, pour prouver que la règle tient aussi pour elle. Inès a déjà trois emprunts en cours. Si Léa lui prête un quatrième tome, la base refuse avec un message clair. Si un autre lecteur veut un tome déjà sorti, c’est refusé aussi. Un emprunt normal passe. Maintenant Inès rend un tome avec la procédure rendre, et elle peut de nouveau emprunter. On a mis cette règle dans la base plutôt que dans l’application parce qu’elle doit tenir quel que soit le chemin : le comptoir, un futur site, ou une requête tapée à la main. Merci, on est prêts pour vos questions. » — REPÈRES : Partie 4 de demo.sql, en tant que lea : la règle tient aussi pour elle. Le trigger emprunts_refuser_emprunt est BEFORE INSERT FOR EACH ROW ; il appelle la fonction emprunts_en_cours. Ensuite la procédure rendre : CALL rendre(200001) passe, Inès peut emprunter à nouveau. Relancer CALL rendre(200001) affiche « Emprunt 200001 déjà rendu », et CALL rendre(999999) affiche « Emprunt 999999 inconnu ». — LES TERMES : BEFORE INSERT : le trigger s’exécute avant que la ligne soit écrite ; s’il lève une erreur, la ligne n’est jamais enregistrée. FOR EACH ROW : il s’exécute une fois pour chaque ligne insérée. NEW : la ligne qu’on essaie d’insérer, lisible dans le trigger (NEW.lecteur_id). RAISE EXCEPTION : arrêter l’opération avec un message d’erreur. Transaction : un groupe d’opérations qui réussit en entier ou s’annule en entier ; c’est pourquoi une procédure qui échoue n’écrit rien. CALL : la commande qui lance une procédure.

QUESTIONS

Ce qu’on peut nous demander

Fonction ou procédure ?

La fonction calcule et renvoie un nombre. La procédure agit, avec CALL, et refuse avec un message.

Pourquoi des rôles NOLOGIN ?

Les droits vont au métier. Si Léa part, on supprime lea sans toucher aux droits du bibliothécaire.

Pourquoi lea lit 4 colonnes d’emprunts ?

Le trigger et la procédure s’exécutent avec ses droits. Aucune de ces colonnes n’est personnelle.

Pourquoi indexer lecteur_id ?

PostgreSQL n’indexe pas les clés étrangères, et le trigger compte les emprunts du lecteur à chaque insertion.

Pourquoi pas dans l’application ?

Dans la base, personne ne peut oublier la règle ni la contourner, même en écrivant dans la table.

D’où viennent 200 000 lignes ?

generate_series, avec chaque colonne calculée à partir du numéro i : lecteur, tome, date.
